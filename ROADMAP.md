# Roadmap

Axon's development has proceeded in informal, numbered phases (see git history and inline comments for Phases 1–7: CS API core, federation foundation + state-res v2, E2EE sync, media/push/app-services, spaces/relations/room upgrades, delegated OIDC login, MSC3814 dehydrated devices). This document tracks what's planned from Phase 8 onward.

## Phase 8 — E2EE reliability & cross-server delivery (done)

Despite a substantial existing E2EE surface (key upload/query/claim, cross-signing, key backup, dehydrated devices), three relay-layer bugs made device verification and message delivery unreliable across clients and homeservers:

- `sendToDevice` never woke a long-polling `/sync` — a queued Megolm room-key share or SAS verification message sat undelivered until the recipient's client-chosen timeout happened to elapse on its own, not until the sender actually sent it. Every existing sync test used `timeout=0`, so this was invisible to the suite.
- `device_lists.changed` only fired on key upload/cross-signing, never on newly sharing a room — a client trusting that signal (rather than deriving key-query needs from room membership itself) would never learn to query/verify a fresh room-mate's devices. `device_lists.left` was hardcoded to `[]`.
- `sendToDevice` had no local/remote split, unlike `/keys/query` and `/keys/claim` — any to-device message aimed at a user on another homeserver was silently dropped forever, since there was no federation EDU handling at all (inbound or outbound).

Fixed by: broadcasting a PubSub wake on to-device delivery (mirroring the existing `device_list_updates` pattern); re-touching `device_list_updates` for both parties on room join and a new `device_list_partings` table + cursor for room leave; and adding `m.direct_to_device` EDU support (outbound via `AxonWeb.FederationFanout`, inbound via `FederationController.send_transaction/2`), plus wildcard (`"*"`) device-id expansion. Regression coverage in `apps/axon_web/test/e2ee_delivery_test.exs` exercises the real long-poll path with a nonzero timeout (closing the test-coverage gap that hid bug 1) and the cross-server EDU path via `AxonFederation.FakeRemoteMatrixServer`.

## Phase 9 — Federation EDU & real-time parity (done)

Full bidirectional EDU support (`m.typing`, `m.receipt`, `m.presence`), building on the `m.direct_to_device` scaffolding from Phase 8, plus durable outbound federation delivery.

- **Typing indicators** (`PUT /rooms/:room_id/typing/:user_id`) were a complete no-op stub — acknowledged and discarded. Now backed by `AxonSync.Typing` (in-memory, auto-expiring, mirroring `AxonSync.Presence`'s design), surfaced in `/sync`'s per-room `ephemeral` section, and federated as `m.typing` EDUs both ways.
- **Read receipts** had no PubSub wake at all (unlike to-device/device-lists/account-data, fixed in Phase 8) — a receipt posted to an otherwise-quiet room sat unseen until something else happened in that room, since incremental sync only included a room at all when it had a *new timeline event*. Fixed with a new `ephemeral_updates` log (mirroring `device_list_updates`) that both wakes long-pollers and makes a room eligible for inclusion on ephemeral-only changes; `m.read` receipts (never `m.read.private`) now federate as `m.receipt` EDUs.
- **Presence** now federates as `m.presence` EDUs to every server sharing a room with the user, but only on an actual state transition (online/unavailable/offline or status_msg change) — not on every `bump_activity` touch, which happens on every authenticated request and would otherwise flood federation peers.
- **Durable outbound delivery**: `AxonFederation.OutboundQueue` persists every outbound PDU/EDU transaction before the first attempt and retries with exponential backoff (30s → 1hr cap, giving up after 7 days) on failure, reusing the same row id as the txn_id on every retry so a remote server that already processed an earlier attempt responds idempotently. Replaces the previous fire-and-forget behavior in `AxonWeb.FederationFanout`, where a failed delivery just logged a warning and was dropped — meaning a remote server being briefly unreachable silently lost whatever was sent to it during that window. Matters here specifically because this deployment federates with other servers in production use, not just same-server accounts.

Regression coverage: `apps/axon_federation/test/outbound_queue_test.exs` (failure → persisted → retry → success), `apps/axon_web/test/phase9_ephemeral_test.exs` (typing/receipt local wake-up and room-inclusion, both EDU directions for typing/receipts/presence, permission checks, expiry).

## Phase 10 — Sliding Sync (MSC4186) (done)

`POST /_matrix/client/unstable/org.matrix.msc4186/sync` alongside classic `/sync` (kept for legacy clients). A pragmatic subset of the MSC rather than full conformance:

- **Lists**: `ranges`-paginated, recency-sorted (`sort` is always treated as `by_recency`) room lists over the user's *joined* rooms, with `is_dm`/`is_encrypted` filters. Every response re-sends a full `SYNC` op per range rather than diffing against a remembered window — no `conn_id` session state is kept, so this is spec-valid but less bandwidth-efficient than real add/remove diffing.
- **`room_subscriptions`**: explicit per-room overrides, included regardless of list ranges; merged with any list config referencing the same room (union of `required_state`, max `timeline_limit`).
- **`required_state` resolution**: concrete `[type, state_key]` pairs, `*` wildcards, `$ME` (substitutes the requesting user), and `$LAZY` (member events lazy-loaded to just the current timeline's senders, plus self) — reusing `EventStore.get_current_state/1`.
- **Extensions**: `to_device`, `e2ee` (OTK/fallback-key counts, `device_lists`), `account_data` (global + per visible room), `receipts` (`m.read` only), `typing` — all built from the same `AxonWeb.SyncHelpers` module classic `/sync` now delegates to as well, so the two endpoints can't drift apart on E2EE/device-list/ephemeral semantics (the extraction this required also served as a small refactor: those cursor/extension helpers used to be private duplicates baked into `SyncController`). Extension params aren't sticky across requests — a client must resend `"enabled": true` every time, not just once.
- **Known gaps, deliberately deferred**: invited/knocked/left rooms don't appear in `lists`/`room_subscriptions` yet (exposing them safely means re-deriving the same invite-state-only visibility rules classic sync's `build_invite_state/2` already enforces — deferred rather than done half-safely); `notification_count`/`highlight_count` are always 0 (this codebase doesn't compute per-room unread/highlight counts anywhere yet, including in classic `/sync` or push dispatch, so this isn't a regression).

Long-poll wake-up reuses `AxonSync.Manager.wait_for_events/3` unchanged, so the Phase 8 wake-up fixes (to-device, device-list, ephemeral) apply here too. Regression coverage: `apps/axon_web/test/sliding_sync_test.exs` (13 tests: list sort/ranges/filters, `room_subscriptions`, `required_state` incl. `$LAZY`/`$ME`, the long-poll wake path with a real nonzero timeout, and every extension).

## Phase 11 — E2EE/verification test hardening (done)

Two real bugs found and fixed while expanding coverage of the surface that's seen the most iterative bugfixing:

- **Stale test, not a stale bug**: `e2ee_multi_device_test.exs` asserted a first-time cross-signing `master_key` upload returns 401 requiring a UIA retry. MSC3967's `uia_exempt?/4` (`key_controller.ex`) correctly exempts first-time setup (nothing on file yet to protect) and has for a while — the test just never caught up. Fixed the assertion and added a real UIA-required case alongside it (rotating to an unrelated master key that isn't signed by the one on file), so the branch that *does* still require UIA has coverage too.
- **Key backup consistency**: `PUT /room_keys/keys` never validated its `version` query param against the user's actual current backup version — a client retrying against a stale, deleted, or superseded version would silently insert rows with no error, and `count`/`etag` on `GET /room_keys/version` would never reflect the write. Now returns `403 M_WRONG_ROOM_KEYS_VERSION` (with `current_version` in the body) per spec, covered by `apps/axon_web/test/key_backup_consistency_test.exs`.

New Complement-style scenario coverage in `apps/axon_web/test/e2e/verification_flow_test.exs`:

- A full `m.key.verification.*` SAS exchange (request → ready → start → key ×2 → mac ×2 → done) between two users' devices, with every hop driven through a real nonzero-timeout long-poll on both sides — not a single event checked with a short poll, which is all any prior test did.
- The same shape across two homeservers via `AxonFederation.FakeRemoteMatrixServer`, with a realistic nonzero timeout on the inbound EDU recipient's long-poll — the existing federation EDU test only short-polled after the fact, so it couldn't catch a wake-up regression on the federated path the way it already could locally.
- The wildcard `"*"` to-device target (`KeyStore.expand_wildcard_device/2`, added in Phase 8) had zero test coverage until now — verified against a 3-device account, confirming delivery to all three and non-delivery to an unrelated user.
- A cross-signing trust-chain scenario: bob signs alice's master key after "verifying" her; `/keys/query` shows bob his own signature but not an uninvolved third party, exercising the visibility rule end-to-end over HTTP rather than just at the `KeyStore` unit level.

## Phase 12 — Room version 12, third-party invites, guest access (done)

Turned out to be a much bigger lift than the original one-line scope suggested: room v12 (MSC4297 + MSC4289) isn't just a state-res tweak, it also changes the room ID format and the power-level model. Implemented for real rather than descoped, since a partial version-12 room would be actively misleading (claiming compliance while silently breaking on the very things that changed).

**Room version 12** (`AxonRoom.CreateRoom`, `AuthRules`, `EventBuilder`, `StateResV2`):
- **Domainless, hash-derived room IDs**: a v12 room's ID is its own `m.room.create` event's ID (reference hash) with `!` instead of `$` — no `:server_name` suffix at all. This is a real chicken-and-egg problem (the room "exists" — DB row, `RoomProcess` — only after the create event is built and hashed, but every other creation step needs the room_id first): `CreateRoom.execute/2` now builds+hashes the create event standalone (`EventBuilder.build/4` with `room_ctx.room_id: nil` omits the `room_id` field entirely, matching the wire requirement that the create event MUST NOT carry one), derives `room_id` from its hash, *then* creates the room row and injects the pre-built event via `RoomProcess.apply_remote_event/2`. `EventStore.event_to_map/1` omits `room_id` specifically for a v12 create event on every outbound path (sync, federation `/state`, `/send_join`, transactions) since it's the single canonical serialization function. Room upgrades to v12 reverse their usual order (new room created first, *then* the old room is tombstoned with the now-known new room_id) since the new ID can't be pre-generated the way every earlier version's `!random:server` id could.
- **Creator privilege (MSC4289)**: a v12 room's "creators" (the create event's `sender` plus any `additional_creators` from its content, passed like any other `creation_content` field) get implicit, infinite power — never listed in `power_levels.users` (a `power_levels` event that lists one is rejected, rule 10.4), can't be outranked or demoted. `additional_creators` is validated as an array of real user IDs at both room-creation time and on any inbound create event.
- **Auth-events selection**: `m.room.create` is excluded from every other event's `auth_events` in v12 (rule 3.2) — fixed in both the local build path (`EventBuilder`) and the federation join/knock/leave template path (`FederationController`), which duplicates that selection logic since remote joins don't go through the normal local build.
- **State-res v2.1** (`AxonRoom.StateResV2`): the one piece that actually matches the original one-line scope — iterative auth checks now start from an empty state map for v12 instead of the unconflicted state map, per MSC4297. The deeper "conflicted state subgraph"/"auth difference over the full conflicted set" refinement wasn't implemented yet at the time, and `AxonRoom.StateResolver` (this module's only caller) only ever resolved one hop of history, so the refinement wasn't reachable through the call path regardless — both fixed for real in Phase 15.6.
- **Defensive fix**: joining/knocking a domainless room_id with no `via`/`server_name` hint used to silently fall back to treating the whole room_id string as a server name (garbage). Now returns a clear `M_MISSING_PARAM` instead.

Regression coverage: `apps/axon_web/test/room_v12_test.exs` (creation, creator/additional_creators power, rule 10.4 rejection, non-creator power gating still works, federation join of a v12 room via `FakeRemoteMatrixServer`, the via-hint error).

**Third-party (3pid) invites** (`m.room.third_party_invite`, `AuthRules.valid_third_party_invite?/3`): `POST /rooms/:roomId/invite` now has a real `medium`+`address` variant that creates an `m.room.third_party_invite` state event (rule 7: gated by invite power) with a token and this server's own signing key, rather than a direct `m.room.member` invite (impossible — no mxid is known yet). `POST /join/:roomId` accepts an optional `third_party_signed` proof, which — if its `signed.token` matches a live invite event in the room and its signature verifies against that event's `public_key`(s) — authorizes the join regardless of the room's normal `join_rule`, exactly like a direct invite would.

Known, deliberate gap: axon has no identity-server integration, so nothing actually delivers a 3pid invite to the invitee (no email/SMS sent) — the room-state mechanics and cryptographic proof are fully real and spec-shaped (self-signed with this server's own key, since there's no external identity server to delegate to), but getting the token to the invitee is left to an out-of-band channel until real mail/identity integration exists. `PUT federation/v1/exchange_third_party_invite` (for a remote server to ask a room-resident server to mint the invite event on its behalf) is not implemented — it would only be reachable once an external identity server both sides trust exists, which axon doesn't provide, so it'd be dead code today.

Regression coverage: `apps/axon_web/test/third_party_invite_test.exs` (invite creation, power gating, valid-proof join, mxid-mismatch rejection, bad-signature rejection).

**Guest access**: audited against spec. The one protocol-mandated, testable guest-specific behavior — `m.room.guest_access` gating on join — was already implemented and tested (`apps/axon_web/test/e2e/guest_access_flow_test.exs`, pre-existing). Didn't find another well-established *protocol* requirement worth adding; further restriction beyond that is a server-policy choice, not a spec requirement, and guessing at additional restrictions risked incorrectly blocking guests from things they're actually allowed to do. No changes made.

## Phase 13 — Operability: admin API & rate limiting (done)

A real admin API under `/_synapse/admin/v1` (mirroring the naming convention the existing shared-secret registration bootstrap already used), gated by a new `AxonWeb.Plug.RequireAdmin` checking `users.admin` — which turned out to be a pre-existing, silently-toothless field: the `admin` flag accepted by the Synapse-compatible bootstrap registration endpoint was parsed and cryptographically bound into its MAC check, but never actually passed through to `UserStore.register/3`, so no account could ever really become an admin before now. Fixed as part of wiring the gate up (the alternative — building an admin API nothing could ever reach — wouldn't have been shippable).

- **User management**: `GET /users` (paginated, filterable by guest/deactivated status), `GET /users/:id`, `POST /deactivate/:id` (admin-initiated; refactored the existing self-service `/account/deactivate` to share the same `UserStore.deactivate/1`), `POST`/`DELETE /users/:id/shadow_ban`.
- **Shadow-ban enforcement** (not just a flag): a shadow-banned user's own non-state (message-like) events are invisible to every *other* local viewer's `/sync` — both classic and sliding — but always visible to themselves (reading your own writes must still work), and never federated out. State events (joins, etc.) stay visible everywhere regardless; hiding those would corrupt other viewers'/servers' picture of room membership, a bigger inconsistency than muting a spammer's messages. Enforced in `EventStore.get_user_events_since/2` and `get_recent_room_events/3` (local sync fan-out) and `RoomProcess`'s federation broadcast (outbound).
- **Room management**: `GET /rooms`, `GET /rooms/:id`, `DELETE /rooms/:id` — a real purge (deletes the room's events/state/memberships/account-data/receipts from local storage) that also marks the room `blocked` so a future join attempt gets a clear, specific rejection instead of silently doing nothing; also terminates the room's live process if one is resident in memory, so it can't keep serving stale state after the rows it was built from are gone.
- **Media quarantine**: `POST`/`DELETE /media/quarantine/:server/:id` — quarantined media is served as a plain 404 (matches Synapse), not a distinct error, so a client/scraper can't use the response shape to tell "never existed" apart from "admin pulled it".
- **Report-review queue**: `GET /event_reports`, paginated — reports were already being collected via the client `POST /rooms/:roomId/report[/:eventId]` endpoints but nothing had ever surfaced them until now.
- **Rate limiting**: a small self-contained ETS-backed sliding-window limiter (`AxonWeb.RateLimiter`, mirroring `AxonSync.Typing`'s GenServer+ETS pattern rather than adding a new dependency for what's a contained need), applied to login (per-IP), registration (per-IP), and message send (per-user) via a controller-level plug. Limits are runtime-configurable (`config :axon_web, :rate_limits`), which is what let `config/test.exs` set them high enough that the test suite's own traffic (many registrations/logins/sends from the same loopback IP across many files) never trips them.

Regression coverage: `apps/axon_web/test/admin_controller_test.exs` (the `RequireAdmin` gate, every admin endpoint), `apps/axon_web/test/shadow_ban_test.exs` (local sync filtering both directions, state-event visibility, federation skip via `FakeRemoteMatrixServer`), `apps/axon_web/test/rate_limit_test.exs` (the limiter directly, and the login plug's 429 shape end-to-end).

## Phase 14 — Feature completion pass (done)

- **Push rules persistence**: `PUT`/`DELETE`/`.../enabled`/`.../actions` on `/pushrules/...` used to silently discard — only the hardcoded server default rule set was ever actually served or evaluated, regardless of what a client tried to customize. Now backed by `AxonPush.UserRules`: a server-default rule (`.m.rule.*`) can have its `enabled`/`actions` overridden but not its `conditions`/`pattern` (fixed, per spec); any other rule id is a genuine custom rule, evaluated before the (possibly-overridden) defaults for its kind. `AxonPush.Dispatcher` now evaluates each recipient's actual merged ruleset instead of always the defaults. Fixed a real bug found in the process: `room`/`sender` kind rules were falling through to generic conditions-based matching, which vacuously matched *every* such rule against *every* event (an empty `conditions` array trivially satisfies `Enum.all?`) — they were simply unreachable before now since no default `room`/`sender` rules exist, but would have misfired the instant a user's custom one became reachable. Not implemented yet: the `before`/`after` positioning query params — see Phase 15.6, which closed this.
- **Server notices**: a lazily-provisioned system account (`@server-notices:<server_name>`) an admin can use (`POST /_synapse/admin/v1/send_server_notice`) to push a message into a dedicated room with any local user, auto-created and auto-joined (not just invited — an invite-only membership can't see timeline content, which would defeat the purpose of a notice) on first use and reused for every subsequent notice to that user, tagged `m.server_notice` in their room account data so a real client can render it distinctly from an ordinary DM.
- **SSRF-safe URL previews**: `GET /_matrix/client/v1/media/preview_url` (previously a deliberate 404) now really fetches and parses OpenGraph metadata, with layered SSRF defense — scheme allowlist, literal-IP and resolved-DNS rejection of private/loopback/link-local/multicast/reserved ranges (IPv4 and IPv6, including IPv4-mapped IPv6), manually-followed and re-validated redirects (capped hops), and response size/time limits. An `og:image`, if present, is fetched through the same hardened path and rehosted as local media so the response returns an `mxc://` URI rather than leaking the original image URL. Results are cached (1hr TTL). Known, documented limitation at the time: not immune to DNS rebinding (the resolve-and-validate check and the HTTP client's actual connection are two separate steps) — see Phase 15.6, which closed this by pinning the connection to the validated address.

Regression coverage: `apps/axon_web/test/push_rules_controller_test.exs` + `apps/axon_web/test/e2e/push_pipeline_flow_test.exs` (a muted room's push rule actually suppresses delivery end to end), `apps/axon_web/test/server_notices_test.exs`, `apps/axon_media/test/url_preview_test.exs` (SSRF blocking and OpenGraph parsing — tested separately by design: real network calls are asserted *rejected* rather than faked, and parsing is exercised directly against canned HTML) + `apps/axon_web/test/media_controller_test.exs`.

## Phase 15 — Production readiness & closing known gaps (done)

The roadmap's originally-planned arc (Phase 8 through 14) was complete; Phase 15 is what it took to go from "feature-complete" to "safe to actually run and to build the next big feature on top of."

### 15.1 — Security-critical config hardening + prod Docker image

`config/runtime.exs`'s `SECRET_KEY_BASE`/`DB_PASS` now hard-fail boot in prod instead of silently falling back to a hardcoded, publicly-known secret (`"a" * 64`) and `axon`/`axon` credentials. New root `Dockerfile` (prod-oriented, non-root user, `HEALTHCHECK`, expects Postgres/secrets from the environment, never auto-runs migrations on boot — distinct from `complement/Dockerfile`, which stays as the Complement test-harness image), `.dockerignore`, `docker-compose.yml`, `.env.example`.

### 15.2 — CI/CD pipeline

`.github/workflows/ci.yml`: test suite against a real Postgres service container, format check, unused-deps check, non-blocking dialyzer (no prior warning baseline, so it reports rather than gates), and a Docker build smoke test of the Phase 15.1 image.

### 15.3 — Observability: telemetry, health endpoints, Sentry

`AxonWeb.Telemetry` wires the previously-declared-but-dead `telemetry`/`telemetry_poller` deps to real Phoenix/Ecto/VM/mailbox-depth metrics, surfaced via Phoenix LiveDashboard at `/_synapse/admin/dashboard` (gated by the existing admin auth pipeline). `GET /health` (liveness) / `GET /ready` (readiness, checks the DB) back the Phase 15.1 Dockerfile's `HEALTHCHECK`. `user_id`/`room_id` now actually populate the Logger console metadata `config/config.exs` had long declared but nothing ever set. Sentry added — no-ops unless `SENTRY_DSN` is set, logger handler only attaches when it is. (Its transport dependency was cleaned up in 15.6 below.)

### 15.4 — Resilience: rate limits + OutboundQueue circuit breaker

Rate limiting (Phase 13's `AxonWeb.RateLimiter`) extended to media upload, URL preview, search, and sync (sync gets a much higher limit than the others since legitimate clients long-poll it continuously). `AxonFederation.OutboundQueue` now caps concurrent in-flight delivery attempts per destination and trips a circuit breaker after 5 consecutive failures — exponential backoff alone only spaced out individual rows' own retries, not the concurrency across different rows becoming due against the same down remote server at once.

### 15.5 — Real-client E2E harness (Playwright + Element Web)

New `e2e-client/` directory: real Element Web instances (matrix-js-sdk) driven by two Playwright browser contexts (Alice + Bob) messaging each other through the actual UI — distinct from `apps/axon_web/test/e2e/*.exs` and `complement/`, both of which are black-box but drive raw HTTP against the Matrix API rather than a real client. Local-dev profile (Axon via `mix phx.server`) and CI profile (the Phase 15.1 prod Docker image) via docker-compose; `.github/workflows/e2e-client.yml` runs it nightly + on manual dispatch (too slow for the PR-blocking loop). First scenario: a DM message round-trip through Element's default encrypted-DM flow. A follow-up fix corrected `element-config.ci.json` pointing the (host-run) browser at a Docker-internal hostname it can't resolve, and installed ImageMagick on the CI runner for `ThumbnailerTest`.

Later in this phase, a second real scenario (`verification-request.spec.ts`) was added while investigating a user report that cross-signing device verification "does nothing" between two users: two real Element Web clients, Alice and Bob, actually driving matrix-js-sdk's own cross-signing bootstrap and verification-request UI against a live Axon server. It passes — proving the server-side mechanism (to-device delivery, cross-signing key upload/query, EDU federation) genuinely works. The real cause of the report was client-side: Element's "Set up Secure Backup" cross-signing bootstrap prompt is a dismissible toast, not a blocking step, and skipping it leaves a user unable to present a clean verification flow to others — a UX trap, not a protocol requirement (you *do* need your own cross-signing keys before you can meaningfully verify someone else, but Element doesn't make that obvious). Also fixed a real, previously-undiscovered bug in `element-config.local.json` (`base_url` pointed at `host.docker.internal`, unreachable from a host-run browser).

### 15.6 — Real state resolution + closing remaining known gaps

The biggest remaining correctness gap: `AxonRoom.StateResolver.resolve_for_auth_check/3` only ever looked one hop into a `prev_event`'s own `auth_events`, so no conflict it produced could span more than one generation — making MSC4297's room-v12 "conflicted state subgraph" refinement (noted as a gap since Phase 12) provably unreachable dead code. Separately, `RoomProcess` applied a forked PDU by overlaying it onto the *old* `current_state` rather than the resolved one, so even that shallow one-hop resolution only ever gated the auth check and was then discarded — a room's state after a real fork was last-write-wins by local insertion order, not spec state resolution.

Fixed in four dependent parts (`apps/axon_room/lib/axon_room/state_res_v2.ex`, `state_resolver.ex`, `room_process.ex`, new `AxonCore.EventStore.get_event_maps/2`):
- **Corrected conflicted/unconflicted split**: per spec, a key present in only *some* input state sets is conflicted (must survive auth-checking to appear in the result at all), not a free pass — the prior split treated it as unconflicted.
- **Real recursive state-at-event resolution**: replaced the one-hop branch builder with a capped, batched, cycle-safe two-phase BFS walk (prefetch, then a memoized fold) that resolves state as far back through locally-known history as a PDU's ancestry actually requires — this is what makes multi-generation forks, and therefore the v12 refinement, reachable at all.
- **`RoomProcess` rebases onto resolved state**: after a fork, `current_state` (and therefore `/sync`, `/state`, restricted-join checks, directory/profile lookups — everywhere room state is read) reflects the real resolved winner going forward, not whatever was last blindly overlaid.
- **The v12 conflicted state subgraph itself**: implemented as a single memoized bottom-up pass (not per-node, avoiding an O(V²) regression) over the conflicted event chain, gated strictly on room v12.

Two more previously-latent bugs surfaced by testing deep enough forks to reach these new paths, both fixed: a sign error in the depth tie-break (`reverse_topological_power_ordering`) that let an older ancestor power-levels event outrank its newer descendants, and a missing spec-mandated `auth_events` fallback in the iterative auth-check loop.

**Federation backfill/catch-up** (new `AxonFederation.Backfill`, `AxonFederation.EventVerification`): closes a related gap the state-res work explicitly flagged as out of scope — when an inbound PDU's `prev_events` reference events axon has never seen, nothing ever fetched that missing history from the origin. Now `AxonWeb.FederationController.process_inbound_pdu/2` detects the gap and calls the origin server's `POST get_missing_events` first (the common "missed one live transaction" case), falling back to `GET backfill` if that doesn't fully close it; fetched events are verified and applied one at a time via the normal `RoomProcess.apply_remote_event/2` path (signature check + auth check + state resolution), oldest-first, same as a live `/send` PDU — they are not pre-vetted the way a `send_join` state snapshot is. Also fixed, while in this code path: `process_inbound_pdu/2`'s unknown-room check used `unless ... do ... end` and discarded the result, so an unknown-room PDU fell through to full signature verification and (now) a wasted catch-up round-trip instead of being rejected immediately.

**Other closed gaps**:
- Push rules now honor `before`/`after` positioning (`PUT pushrules/.../{kind}/{ruleId}`) instead of always appending in creation order (closes the Phase 14 gap).
- URL preview fetches (`AxonMedia.UrlPreview`) now pin the HTTP connection, via Mint, to the exact address that was SSRF-validated, closing the resolve-then-connect DNS-rebinding gap the Phase 14 SSRF hardening left open.

## Phase 17 — Triaging the Complement `tests` package

Phase 16 left the `tests` package (general + federation black-box conformance) at **10/89 (~11%)** with the failures explicitly untriaged: "whatever's failing here is mostly a different, larger set of individually-untriaged gaps — ACLs, device-list-over-federation edge cases, restricted-room joins, media, and more". This phase worked through that list cluster by cluster. It ends at **22/89 (~25%)** with **zero regressions** — still a minority, and the package still exits FAIL. The more useful result than the number is *what* the failures turned out to be: a few were one systemic bug each holding down a whole group of tests, and several were entire endpoints or features that had simply never been implemented at all (federation invites in both directions, `event_auth`, `/context`, the authenticated federation media endpoints, and server-ACL enforcement anywhere).

### The systemic one: `send_join`/`send_leave`/`send_knock` never relayed onward

`RoomProcess.apply_remote_event/2` never re-broadcast an applied PDU to federation at all. That's correct for an ordinary `/send` transaction PDU — the origin server already pushed it to every resident server itself, and relaying further would duplicate traffic and risk amplification loops. But it's wrong for `send_join`/`send_leave`/`send_knock` specifically: the acting user's own server structurally *cannot* fan the new membership event out to the room's other servers, because it only just learned the room exists (and who is in it) from this very request, and has only ever talked to the one resident server it went through. The resident server is the only party with the full membership picture — and it was silently telling nobody.

The consequence is that **a room with three or more homeservers never converged on membership**. Each newly joined/knocked/left server's peers never learned about it unless they happened to receive the event by some other route. This is what made `TestACLs` fail on its own control group (the sentinel room, which has no ACL at all): charlie could not see bob's message because charlie's *join* had never been relayed to bob's server in the first place.

Fixed with an opt-in relay: `RoomProcess.apply_remote_event/3` takes `relay_exclude: server_name`, which — only when set — fans the just-applied event out over the same `federation:fanout` PubSub path local sends use, excluding the server that just handed us the event (it already has it). `FederationController` passes the requesting origin from all three `send_*` handlers; every other call site (ordinary `/send` PDUs, `Backfill` catch-up, v12 room creation) keeps the previous no-relay default unchanged.

Found in the same code while adding coverage: `send_leave` had **no type/content validation whatsoever**, unlike its `send_join`/`send_knock` siblings — any signed, auth-valid event from a joined member (an ordinary message, say) was accepted and applied through it. And all three now reject a mismatched `state_key`/`sender` with `400 M_BAD_JSON` directly rather than falling through to `AuthRules` and surfacing as `403`; these are self-action-only endpoints, so a mismatch is a malformed request, not an authorization failure.

### Server ACLs were enforced nowhere

`m.room.server_acl` appeared in exactly two places in the codebase — as a default power-level entry in `CreateRoom`, and in `RoomUpgrade`'s copied-state list. Nothing ever *evaluated* one. A server named in a room's `deny` list kept sending messages, joining, and posting read receipts entirely unimpeded.

New `AxonRoom.ServerAcl` implements the spec's algorithm in order (no ACL event → allow; IP literal with `allow_ip_literals: false` → deny; `deny` match → deny; `allow` match → allow; otherwise deny), with case-insensitive glob matching (`*`, `?`), the port stripped before matching (`evil.com`, `evil.com:8448` and `evil.com:1234` must all match a rule for `evil.com`), and bracketed-IPv6 handling so `[::1]:8448` isn't shattered by a naive split on `:`. Deliberately kept out of `AuthRules`: the spec is explicit that ACLs "do not restrict the events relative to the room DAG via authorisation rules, but instead act purely at the network layer", so a server denied by an ACL added *after* it already has events in the room keeps them — only its further traffic is rejected.

Wired into every endpoint the Server-Server API's ACL section marks MUST-protect (`make_join`/`make_leave`/`make_knock`, `send_join`/`send_leave`/`send_knock`, `state`, `state_ids`, `backfill`, `get_missing_events`, `event_auth` → `403 M_FORBIDDEN`), plus per-PDU gating on `/send` (soft-failed, not applied) and per-EDU gating on `m.typing`/`m.receipt` (dropped).

Chasing the EDU half of this surfaced an unrelated real bug: an **initial** (`since`-less) `/sync` attached an `m.typing` ephemeral entry to *every* joined room even when nobody was typing. `build_typing_event/1` assumed — correctly for incremental sync, per its own comment — that a room only appears in the response because something ephemeral changed, making an empty `user_ids` list a meaningful "someone stopped typing" transition. That assumption doesn't hold for an initial sync, which includes every joined room unconditionally. The ACL-denied room in `TestACLsForEDUs` was leaking exactly this spurious entry.

### Three endpoints that were never implemented

- **Federation invites** (`PUT /_matrix/federation/v2/invite/...`, both directions). Inviting a remote user was a complete no-op from their side: the CS API invite handler always built a *local* `m.room.member` event regardless of the target's server, and nothing anywhere spoke the federation invite handshake — no outbound call, and no inbound route either, so a remote server inviting one of our users just got a 404. Outbound now builds and self-signs the event through the same `EventBuilder`/`AuthRules` a local invite uses (so an inviter without invite power is rejected up front, not only in the same-server case), round-trips it through the target's endpoint to collect their signature, and applies the result via the normal remote-event pipeline. Inbound validates the event and persists it *without becoming resident* — a bare membership row plus the sender's `invite_room_state` preview, which is exactly what `invite_state` needs, mirroring how knocks already store a preview. Rejecting such an invite needed its own path too (`AxonFederation.RoomLeave`): a room known only via a federated invite has no local `RoomProcess` to leave through, so `POST /rooms/:id/leave` now detects the absence of a local create event and goes out via `make_leave`/`send_leave` instead of silently discarding the invite locally.
- **`GET /_matrix/federation/v1/event_auth`** — no route at all. Returns the requested event's full transitive auth chain (ancestors only), reusing the same recursive walk `get_state`/`get_state_ids` already use.
- **`GET /rooms/:room_id/context/:event_id`** — no route at all, so it 404'd generically. Returns the target event plus a window of surrounding timeline (split from `limit`, reverse-chronological before / chronological after, target excluded from both) and the room's current state, behind the usual membership gate.

### Media: authenticated federation media, and a filename that was thrown away

Remote media fetching spoke *only* the deprecated, unauthenticated `/_matrix/media/v3/...` endpoint, hardcoded to `https://<origin_server>/` — no federation TLS port resolution, no X-Matrix signing. That only ever worked against a server reachable on plain port 443 with no auth required, which is never true of another axon/Complement instance and increasingly untrue of any spec-compliant server. There was no inbound support at all either: nothing served axon's own media to another server over the authenticated endpoint.

Both directions now exist (MSC3916 / Matrix 1.11): `GET /_matrix/federation/v1/media/{download,thumbnail}` serves local media as `multipart/mixed`, and `AxonFederation.MediaFetch` fetches from the same endpoint on the remote, parsing the multipart response (including a `Location` redirect in the file part). Fallback to the deprecated endpoint (with `allow_remote=false`, per spec) happens on a `404 M_UNRECOGNIZED` — the spec's defined signal — and also on a `400`, which is not spec-mandated but is what a server whose authenticated-media handler is broken or absent tends to answer a well-formed GET with; hard-failing a user's download over that helps nobody when the deprecated endpoint works. A `403` or `5xx` still propagates as-is. (Complement's own federation test double is such a server: `HandleMediaRequests` reuses the legacy handler — which validates an `{origin}` path variable — for the authenticated route, whose path has no such variable, so it unconditionally 400s. Preferring the authenticated endpoint is what briefly regressed `TestMediaWithoutFileName` mid-phase.)

Separately: `?filename=` was parsed at upload time and **immediately discarded**, and every download hardcoded `Content-Disposition: inline` with no filename at all. Now persisted (new `media.filename` column) and returned, with `inline` reserved for the spec's "safe to render" content-type allowlist and `attachment` for everything else; ASCII names go out as a quoted-string (which handles embedded spaces and semicolons once quoted), non-ASCII via RFC 6266's `filename*=UTF-8''<pct-encoded>` form. Proxied remote downloads carry the remote's filename through too.

Fixing outbound media also exposed a latent bug in `AxonFederation.ServerResolver`: a failed `.well-known` lookup appended a *second*, default `:8448` even when the `server_name` already carried its own port, producing an unparseable double-port authority. An explicit-port `server_name` now skips well-known entirely, per the server-name resolution spec. Unreachable before, since nothing had resolved an arbitrary explicit-port `server_name` through that path.

### Room v12: the create event's `room_id` was being stripped from *client* responses too

MSC4291's "the create event carries no `room_id`" rule is a **federation PDU** rule — the room ID is that event's own reference hash with `!` for `$`, so the field is redundant on the wire, and its presence would change the content hash and make a receiving server compute a different event ID. Phase 12 implemented it inside `EventStore.event_to_map/1`, described at the time as "the single canonical serialization function" used on every outbound path. That description was precisely the problem: the same function also feeds the entire Client-Server API, whose `ClientEvent` schema requires `room_id` unconditionally. Every client-facing view of a v12 create event — `/sync`, `/state`, `/messages`, `/event/:id`, `/context`, `/state?format=event` — was silently missing it.

Split into two explicit functions: `event_to_map/1` (client form, always keeps `room_id`) and `event_to_pdu/1` (federation form, omits it for a v12 create only). All eight serialization sites in `FederationController` and both `broadcast_for_federation` call sites in `RoomProcess` use the PDU form; every CS API caller keeps the client form. Two existing tests asserted the old behavior through the client form and were corrected to pin the real distinction — both now assert *both* forms explicitly so the two can't silently re-converge.

### The bug that mattered most, and why no amount of reading found it

`make_join` answered `403 M_FORBIDDEN "User ID domain does not match origin"` for any user whose server name carries an explicit port. 26 call sites across 8 files derived a Matrix ID's server with

```elixir
id |> String.split(":") |> List.last()
```

which returns the **port**, not the host: `"@charlie:host.docker.internal:41491"` yielded `"41491"`. Every federation endpoint comparing that against the requesting origin rejected the request. Complement addresses every remote homeserver as `host.docker.internal:<port>`, so this failed the *setup* of whole test families long before their actual assertions ran.

This is why an earlier worker's careful static analysis of the `send_join`/`send_leave`/`send_knock` validation cluster correctly found **no bug** — it traced every assertion in Complement's shared helper to code that already satisfied it, and said so, and reported that if those tests were still red the cause had to lie outside that file. It did. The lesson is recorded here deliberately: a well-argued negative result from a worker is a finding, not a failure, and overruling it would have meant "fixing" correct code.

Replaced by `AxonCore.MatrixId.server_name/1` — split on the *first* colon, since sigil and localpart can never contain one — returning `nil` for an ID with no server part at all, notably a room-v12 room ID (a bare hash by design, MSC4291). `room_controller`'s v12 via-hint check had been detecting that case by relying on the old buggy behaviour (`room_server == room_id`) and now tests the `nil` directly.

### Real bugs found and fixed

- **A knocking user could join without an invite.** `check_join`'s `knock` branch accepted `knock` as a valid prior membership for a self-service transition to `join`. Spec rule 4.3.4 permits only `invite`/`join`. Found by a worker while fixing something adjacent, and not by the triage that preceded it.
- **Room creators could be outranked.** `@infinite_power` was `1_000_000_000`, but a power level is a JSON number a client may legitimately set as high as `2^53 - 1`. An admin promoted above the constant outranked the room's own creator, and the creator failed to outrank them — both directions broken. Now `10^18`, with a new auth rule rejecting any `power_levels` value outside the canonical-JSON-safe integer range.
- **Rejected events were never persisted.** The `rejected`/`soft_failed` columns were read in a dozen places and written in *none*; an event failing auth was silently dropped. Now stored with `rejected: true`, excluded from derived state, and "unrejected" with a fresh `stream_ordering` on a passing resend (a stale ordering would sort the event before any `since` token a client already holds, so it would never appear in `/sync`).
- **Events with unknown ancestry were accepted anyway.** When a PDU's `prev_events` could not be resolved, `StateResolver` fell back to the room's *current* state, authorising the event against unrelated state. It now refuses. Narrowed deliberately to "all prev_events unresolvable" so the existing, tested partial-merge behaviour survives.
- **`m.device_list_update` existed nowhere.** Phase 8 built the local device-list machinery; nothing ever federated it, in either direction. A remote server was never told a local user's devices changed.
- **`m.room.server_acl`, `/publicRooms` and aliases**: `/publicRooms` never returned `join_rule` or `room_type` at all, breaking the public-room half of its own test as well as the knock half; `DirectoryController.can_manage_aliases?/2` did its own power arithmetic and so did not know about v12 creator privilege.
- **Space hierarchy** recursed into any room's `m.space.child` links rather than only spaces, was breadth-first where the spec's pagination requires depth-first pre-order, had no pagination at all, and never consulted a restricted room's `allow` list when deciding visibility.

### Endpoints that simply did not exist

`GET /_matrix/client/v3/notifications`; room tags (`/user/{userId}/rooms/{roomId}/tags`); generic profile fields (stable since Matrix 1.16 — verified on the spec page before building, rather than trusted from the audit); `timestamp_to_event` in both the client and federation directions; `room_summary`; federation `hierarchy`; federation `version`; `power_level_content_override` on `createRoom`; and proper `404`/`405 M_UNRECOGNIZED` handling for unknown endpoints, which previously answered `M_NOT_FOUND` and had no notion of 405 at all.

### Unread notification counts

Phase 10 recorded these as always-0. That was already half-stale — Phase 15 had implemented real counts for sliding sync — so the work was to promote that logic into `AxonWeb.SyncHelpers` shared by both sync endpoints (so they cannot drift), and add a persisted notifications ledger written by `AxonPush.Dispatcher` to back `GET /notifications`. Counts stay on-the-fly rather than in a counter table: a counter must remain correct as a read receipt moves *backwards* as well as forwards, and silent drift is worse than a bounded rescan. `unread_thread_notifications` is deliberately absent — there is no per-thread receipt model to compute it from.

### Infrastructure traps found the hard way

- **The host's Postgres was dead** for the whole phase: the box now has PostgreSQL 18 binaries against a v16 data directory, so the service refuses to start. Not migrated — that data directory is shared with unrelated projects and the migration is the owner's call. Worked around with a disposable `postgres:16-alpine` container.
- **The test suite cannot be run twice concurrently on one host.** `AxonFederation.FakeRemoteMatrixServer` binds fixed ports; a collision crashes the listener and cascades into the whole `axon_web` application shutting down, which presents as 440 of 441 tests failing with a missing ETS table. Environmental, not a regression — but indistinguishable from catastrophe if you only read the summary.
- **The README's "fast incremental" Complement image rebuild cannot work on this host, and fails silently.** It copies a release built on Fedora (glibc 2.38) into a Debian bookworm image (glibc 2.36); every homeserver container then dies at boot with a `GLIBC_2.38 not found` link error, and Complement *hangs* waiting on servers that never come up rather than failing loudly. Cost a wasted 23-minute run. `_build/` is excluded in `.dockerignore` precisely to prevent this; the exclusion was removed during this phase to "fix" the recipe and had to be put back, with the reason recorded in both files. A single-test smoke check before any long run is now the standing practice.
- **A 500ms poller with no Ecto sandbox ownership** (the new device-list fan-out) crashed on every tick under test, exhausted its supervisor's restart intensity, and took down the `axon_federation` application — failing 96 unrelated tests with a missing-ETS-table error that pointed nowhere near the cause. Failed polls are now skipped.

### Where it stands, honestly

**35/89.** The package still exits FAIL and 54 tests remain red. What changed beyond the number is the quality of the remaining information: there is now a per-test first-failure extract for every failing test, so the next pass starts from evidence rather than from test names.

Known and unresolved at the end of this phase:

- **A second systemic federation bug is still open.** Outbound `make_join` to a peer is answered `401` and the *receiving* server logs nothing — which should be impossible, since every rejection path in `AxonWeb.Plug.FederationAuth` logs a warning. This gates `TestJoinViaRoomIDAndServerName`, `TestOutboundFederationSend`, the restricted-room remote joins, and plausibly `TestKnocking` (which dies at `502 Failed to deliver invite to remote server` during setup). Under investigation; not diagnosed.
- **`soft_failed` is still never set.** Axon has only one auth check, against ancestor-resolved state, and no second check against current state from which a genuine soft-failure signal could be derived. Rejection is implemented; soft-failure is not.
- **`AuthRules` rule 2 is unimplemented** — an event's `auth_events` are never checked against what the selection algorithm would have chosen.
- **`TestEventAuth` remains genuinely un-root-caused.** The endpoint exists and returns a correct transitive chain; the field name matches the Go client's struct; the selection algorithm was traced and looked right. Recorded as UNKNOWN rather than given a plausible-sounding cause.
- The per-room summary field building is duplicated between `SpaceController` (per-user visibility) and `FederationController` (per-server visibility). The visibility rules genuinely differ; the field assembly does not, and belongs in a shared module.
- The `msc*` packages remain expected failures, unchanged since Phase 16.
